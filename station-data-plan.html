地铁站卡片内容：数据源调研 + 玩法定案

2026-10-10 · 针对「676 站（北京 410 / 南京 266）附近有什么值得逛」这件事，实测了 5 类数据源，下面是结论与建议
结论先行
  1. 不存在「别人整理好的每站打卡清单」这种现成数据集——无论是开源社区还是商业 API，都没有按「地铁站 → 值得逛的点」这种粒度整理好的中文公开数据。
  2. 但可以用四层拼出来，而且我已实测验证其中三层可跑：OSM（免费可分发、城区质量好）、文保单位名录（权威、专补冷门）、LLM 生成（补空白）、UGC（长期）。
  3. 真正的瓶颈不是"拿不到数据"，是"冷门站恰恰没有数据"——你最想要的祠堂/墓/碑这类冷点，公开 POI 覆盖率最低。这一层只能靠文保名录 + UGC。
  4. 有个硬约束必须先知道：高德/百度 POI 的服务条款禁止离线存储与再分发。你的游戏是单文件发在 GitHub Pages，所以这条路只能「运行时调用」，不能「烘焙进 HTML」。

冷站悖论：你之前明确说过想要「冷门历史现场优先（祠堂/墓/碑等冷点）」。但实测下来，公开 POI 数据恰恰在冷站是空白——热门商圈一堆，郊区古碑一座没有。
所以「自动抓取」只能解决热门站；冷站必须走 文保名录 + UGC，这是绕不开的。

两个工程坑（真跑出来的）

  • Overpass 有严格限流：连续请求会返回 429 / 504；一次性拉全市必超时。必须分片（4×4=16 块）+ 镜像轮询 + 重试 + 去重。我实测 16 片里失败了 8 片，其中正好包含主城区——所以任何"一次跑完"的脚本都得写容错。
  • 噪声数据：世界公园里的微缩景观（Abu Simbel Temples、Arc de Triomphe）会被当成真 POI 抓进来。必须做类别白名单 + 名称黑名单 + 文保/百科标记优先的降噪。

二、推荐的数据分层架构

不要指望单一数据源吃下 676 站。四层叠加，每层补上一层的洞：

L1 事实层 · OSM → 自动抓，给城区站「附近有什么」的客观清单
L2 权威层 · 文保单位名录 → 按坐标匹配，专补冷门站的历史现场（祠堂/墓/碑/遗址）
L3 生成层 · LLM → 对 L1+L2 都为空的站，用站名 + 片区 + 线路信息生成一版草稿，标注「未核实」
L4 众包层 · UGC → 玩家补充真实推荐（哪家店、哪个门、怎么走），带审核与信誉
源透明度必须贯穿始终（这是你在明朝项目里反复强调的纪律）：每一条内容都带来源标记 osm / 文保名录 / AI生成 / 玩家投稿，卡片上直接显示。 不能让玩家把 AI 草稿当成已核实的事实。

三、UGC + 后端同步：可以直接复用你现有的东西

你在 BSRI 项目里已经跑通了 Cloudflare Worker + 匿名 128-bit uid 这套。地铁卡片 UGC 用同一套技术栈最省事：

存储

  • D1（SQL）：投稿表 (station_id, city, kind, text, author_uid, ts, status, votes)
  • KV：审核通过的内容缓存，前端一次拉全量（676 站的内容也就几百 KB）
  • 本地 localStorage 存「我投过什么 / 我点亮了什么」，离线可玩

接口（Worker）

  • GET /tips?city=bj 拉已通过投稿
  • POST /tip 投稿（进待审队列）
  • POST /vote 点赞 / POST /report 举报
  • GET /mine?uid= 取回我的投稿

防滥用（UGC 必做）

  • 投稿先进待审，不直接上线
  • 简单规则过滤：广告词、外链、手机号
  • 信誉分：投稿被采纳 +，被举报 −
  • 每人每天投稿上限（如 5 条）
一个必须提前想清楚的问题：UGC 一旦开放，内容质量和合规责任就转移到你身上。 「某某餐厅好吃」是主观推荐还好；但涉及价格、营业时间、医疗、安全类信息就会过期并可能误导。 建议只允许投「值得逛 / 值得吃」这类主观推荐，禁止投事实性断言，并在卡片上统一标注「玩家投稿 · 未经核实」。

四、艾宾浩斯：怎么让「记住」真的发生

先说一个反直觉的判断：单纯的复习弹窗会毁掉这个游戏。贪吃蛇是 150ms 一拍的实时玩法，任何"停下来答题"的打断都会让人烦。所以复习机制必须长在游戏里，而不是挡在游戏前。

关键设计一：记忆等级 = 收集的第二维度

不要做两套系统。现在是「吃过 + 读过卡 = 点亮」一维。建议加第二维：记忆等级（铜 → 银 → 金 → 钻）。 点亮只代表"见过"，金/钻才代表"记住了"。这样"收集"和"记住"是同一个进度条的两个轴，而不是两个互不相干的玩法。

关键设计二：复习的最小单位要拆成「可判对错的一条事实」

SRS 只能测有标准答案的东西。所以卡片那段介绍文字不能被整体复习，必须拆成原子事实：

站点：菜市口
├─ fact#1  附近有康有为故居          ← 可出四选一
├─ fact#2  附近有湖南会馆            ← 可出四选一
└─ fact#3  是 4 号线与 7 号线换乘站   ← 可出四选一

干扰项从同城同类 POI里抽（其他站的景点/故居），难度自然可控，而且顺便帮你记住别的站。

关键设计三：触发方式（三选一，建议 C）

A · 主动自习室

独立入口，每天登录后列出到期站点，逐条答题
  • + 最纯粹，遗忘曲线执行得最准
  • − 和主玩法完全分离，像在做作业，玩蛇的人不会点

B · 被动嵌入

玩的时候，到期站点在地图上发光；吃到该站豆子时先提问再给答案
  • + 不打断节奏，复习自然发生
  • − 到期站点不一定被走到，覆盖率不可控；且"边跑边答"压力大

C · 混合（推荐）建议

默认走 B，攒够一定数量后主入口提示「今天有 N 站该复习」
  • 局内：到期站在小地图/视野里微微发光（复兴号），吃到时弹「回忆卡」——先出四选一，答对升级答错降级，然后才展示原卡片
  • 局外：主入口常显徽章「今日待复习 12 站」，点进去是 30 秒快速问答（A 模式）
  • 节奏：复习是可选的加分项，不是强制门槛——不复习也能玩，复习了升级快

间隔怎么定

记忆等级含义下次复习间隔答错
铜刚点亮1 天退回铜级，
间隔重置
银答对 1 次3 天
金答对 2 次7 天
钻答对 3 次21 天（之后转长期）

间隔按真实时间（跨会话、存时间戳），不是游戏内时间——否则艾宾浩斯没有意义。

奖励闭环（让复习有动力）

  • 答对 → 该站记忆等级 +1，同时给一点点游戏内收益（如 +1 节长度 / 短时加速），让"记住"直接兑现成"变强"
  • 一条线所有站都到金级 → 解锁该线「线路徽章」+ 线路专属外观
  • 成就大图上用颜色深浅表示记忆等级（现在是三态：没去过/吃过/点亮，变成五态）

五、不同线路的收集模式

现在是「全网点亮获胜」单一目标。可以加的维度：

A · 线路徽章（按线独立结算）

每条线集齐所有站 → 该线徽章；短线和长线难度天然不同
  • + 最简单，和现有「电流蔓延」进度条天然契合
  • + 短线（如南京 S9 只有 6 站）给正反馈快，长线（北京 10 号线）是长期目标
  • − 只是把总目标拆开，没有新玩法

B · 线路专精（等级制）建议和 A 叠加

每条线有独立等级 = 站点收集率 × 平均记忆等级
  • + 把「收集」和「记住」绑在一条线上，正是上一节的核心思路
  • + 升级解锁该线专属皮肤/能力（如 2 号线"环线"给转向冷却 −1）
  • − 需要设计 28 条线各自的奖励，工作量大

C · 枢纽任务（跨线联动）

围绕换乘站设计组合任务：「在 3 条线的枢纽站各点亮 1 个」「一次换乘走完 2 号线 + 6 号线」
  • + 让换乘玩法有目的，不只是换条线继续吃
  • − 任务设计容易变成清单打卡

D · 轮换赛季

每周一条「本周特选线路」，进度双倍，过期不候
  • + 制造回访理由，适合长期运营
  • − 和"全网点亮"的长期目标有冲突感
我的建议：A + B 叠加，暂不做 C / D。
徽章（A）解决"短线给正反馈"，专精等级（B）解决"记住了要被看见"，两者共用同一套进度数据。 C 和 D 等主线跑顺了再加——现在加只会让目标体系变复杂。

六、需要你拍板的三件事

① 数据先做哪一步？
  • 选项 1（推荐）：我先跑通 OSM 自动化，产出北京 + 南京全部 676 站的初版结构化数据（含坐标、附近 POI、来源标记）。跑完你看质量再决定要不要接文保名录和 UGC。
  • 选项 2：只做小样本（20 个代表性站点，热/中/冷各几座），先验证「自动生成的卡片到底好不好看、有没有用」，再决定要不要铺全量。
  • 选项 3：先跳过数据，直接做 UGC 后端 + 艾宾浩斯复习机制，内容靠现有的 101 条手写卡先跑起来。
② 要不要接高德 POI？
  • 接 → 内容质量最高最本土，但只能运行时调用（不能内置进单文件），且你要提供 key、接受配额。
  • 不接 → 全部走 OSM + 文保 + UGC，可内置、可离线，但冷站偏空、餐饮类几乎没有。
③ 冷站（郊区古碑/祠堂）的内容怎么办？
  • 去国家地球系统科学数据中心下那份 5058 处文保单位空间数据集（需注册），按坐标匹配到地铁站 —— 这大概是最有针对性的一步。
  • 或者接受冷站暂时空白，靠 UGC 慢慢填。
顺带一个已有数据的问题：南京 6 号线官方是 19 站，项目里写的是 20 站；北京昌平/房山/燕房/亦庄T1、南京 5/7/10/S4/S6/S8 的站序也还没抽查。 如果要铺全量数据，建议先把站序校准——不然坐标会配错站。GitHub 上 narutogo/china_subway 有全国各线站序，可以用来做交叉校验。
