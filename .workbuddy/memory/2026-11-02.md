## 对 su77315 固定房间做严格自查：找出 4 个真问题

用户要求「严格自我检查纠错，然后改进」。没有停在「看起来没问题」，逐项查了路径、协议、渲染、响应式。

### ① 多人页跳转 404（严重，已修）
`bell/multi/app.js` 里 `gotoDuel` 写的是 `window.location.href='./duel/?room=SU77315'`。
但**这个页面在 `/bell/multi/`**，`./duel/` 会解析成 `/bell/multi/duel/` → 404。
双人页 `bell/app.js` 用 `./duel/` 是对的（它在 `/bell/`）。
→ 改成 `../duel/?room=`。
**教训：相对路径按「当前页面所在目录」解析，不是按仓库根。多页面共用同一段跳转逻辑时最容易错。**

### ② 多人页必须填昵称才认房间码（体验 bug，已修）
`choose(which)` 里昵称校验在房间码判断之前：
```js
const nickname=cleanName(...); if(!nickname){toast('先输入你的昵称');return;}
...
code=$('joinCode').value...; if(code===DUEL_CODE){gotoDuel();return;}
```
结果：只拿到房间码的人点「加入」会被「先输入你的昵称」挡住。
→ 把 `if(which==='guest'){ code=...; if(code===DUEL_CODE){gotoDuel();return;} }` 提到昵称校验之前。

### ③ 野连接断开会把真正客人踢掉（协议 bug，已修）
`onGuestGone()` 原来不接受参数，用的是全局 `guestConn`：
```js
function onGuestGone(){ const pid=guestConn&&guestConn.peer; ... }
```
`guestConn` 只保留「最近一条连接」。同一个人开第二个标签页、或有人扫到链接连一下就断，
那条野连接关闭时会读到 `guestConn` = 真正客人的连接，**把真正客人的座位清掉**。
→ 房主侧改成按连接记账：`let conns=new Set()`，`fromGuest(c,d)` / `onGuestGone(c)` 都带连接参数，
`broadcast` 遍历 `conns`。关闭/出错用 `c.__gone` 防重复清算。
→ 新增测试 [10]：野连接 fire('close') 后 315 座位仍在、消息仍被处理、广播仍能到达。

### ④ 内联 style 盖掉媒体查询（响应式，已修）
duel 页为了两列牌桌把 `.play-card` 覆盖成 `width:min(100%,132px)`，
但内联 `<style>` 在 `<link>` 之后 → 连 `style.css` 里 `@media(max-width:720px){.play-card{width:72px}}`
和 `360px` 那档一起盖掉，小屏牌会撑出格子。
→ 覆盖时把两档断点补回来。

### 其他小修
- 客人点座位到房主回执之间，自己的座位会显示「空着，等人来」→ `pickSeat` 先乐观占位，
  `reject` 时把两边座位清空（否则回选座页再选另一边会残留「已坐下」）。
- 牌桌上自己的座位显示「轮到 TA 翻牌」→ 改「轮到你翻牌」。
- `?room=SU77315&seat=315` 的说明文案原来写成「或 &seat=315」，改成「把最后的 77 换成 315」。

### 测试从 41 → 55 项
新增：渲染文本断言（名单/牌桌真的出现 77 与 315、轮到谁）、
**JS 跳转路径静态审计**（解析 `location.href='...'` 到文件系统，直接抓 ①）、
被拒后清空占位、野连接隔离。

### 通用教训
- 「自查」要按**维度**过：路径 / 协议 / 渲染 / 响应式 / 文案，每个维度单独找证据，
  不要只看「我记得我写对了」。
- 静态审计很便宜且有效：把所有 `location.href='...'` 按页面目录解析一遍，5 行代码就能抓出 404。
- 测试 harness 的 stub 不解析 HTML 初始 class，也不累积 `textContent` —— 后者改造后
  才能断言「渲染出来的字对不对」，比只断言内部状态更接近真实。

## 「对方说进来了，我这边不显示」——联机进入环节的根因与重做

用户反馈：很多时候对方说进来了，他那边没显示。逐条排查后确认**四个独立原因**，
其中两个是「界面在骗人」，两个是链路真的断了。

### ① 界面在骗人：点完座位就在本地标成「已坐下」（最要命）
`pickSeat` 里 `seats[seat]={here:true,...}` 是**乐观占位**，没有任何服务端确认。
数据通道根本没建起来时，客人这边也显示「1/2 人 · 已坐下 · 未准备」，
于是出现「我明明进来了啊」的对话僵局。
→ 改成三态：`joined` 只由房主的 `welcome` 置 true；未确认前座位显示「正在进入…」，
`connected()` 也要求 `joined`，没连上就点不动翻牌/抢铃。

### ② 链路真的断：PeerJS 默认只用 Google STUN
PeerJS 公共服务的默认 `iceServers` 是 `stun:stun.l.google.com:19302` + twilio。
国内这个 STUN 基本不通 → 只剩 host（局域网）候选 → 跨网络 100% 建不起通道，
而信令层面看起来「连上了」，于是两边都没有报错。
→ 统一换成：`stun.qq.com` / `stun.miwifi.com` / `stun.chat.bilibili.com` 为主，
Google/Cloudflare 兜底，再加 `openrelay.metered.ca` 的免费 TURN（对称 NAT 只能靠 TURN）。
`bell/duel`、`bell/multi`、`bell/app`、`watch`、`turtle` 五处一起换。

### ③ 掉线后永远回不来：座位被自己的幽灵连接占着
房主侧原来只判断 `seats[seat].here`，客人一断线重连就收到「座位已经有人坐了」。
而房主那边的 `seats[1-mySeat].here` 在 `cleanupPeer()`（换角色/重建 peer）时**不会被清**
→ 幽灵座位永久存在，客人怎么也进不来。
→ 两处修：`resetOccupancy()` 在换角色时清空；`join` 时按「旧连接是否还活着 / 是否同一个
`CLIENT`」判断，本人重连直接接管旧连接，陌生人才拒。
→ `CLIENT` 存 localStorage，作为「同一台设备」的判据。

### ④ 悄悄死掉的连接没人发现
WebRTC 数据通道可以在双方都不报错的情况下停止工作，界面就一直挂着「已坐下」。
→ 加心跳：房主 1.5s 广播 `{type:'hb'}`，客人 3s 发 `ping`；
房主看门狗 9s 没收到客人消息就清座，客人 6.5s 没收到房主消息就主动重连。

### 顺带
- `?seat=` 直达 + 房间栏加「重新连接」按钮（手动重建链路，比重开页面省事）。
- `visibilitychange` 回前台时若已断线自动重连（手机切后台必踩）。
- 重连**保留同一个 peer id**：以前每次重试都 `new Peer()`，房主那边堆一串野连接，
  最后自己反而被「座位已有人」挡住。
- 加 `probeHost()`：用一个临时 peer 探固定 id 是否空出来了，抢到就接管当房主，
  比干等服务器释放 id（约 60s）快得多。
- 房主 peer 的 `open` 可能因信令重连再触发一次 → 那里**不能无脑清座位**，
  要先保留仍然 `open` 的连接对应的座位。

### 测试 55 → 78 项
新增：握手前不许显示已坐下、`welcome` 后才 `joined`、
同一 `CLIENT` 重连接管 / 陌生人抢座仍拒、房主重建后无幽灵座位、
信令重连不清在座的人、**假时钟驱动的心跳看门狗**（6.5s 无消息 → 自动重连）、
探测接管固定 id。
假时钟做法：sandbox 里替换 `setTimeout/setInterval/Date`，`advance(ms)` 按到期时间
排序执行，`Date.now()` 跟着走 —— 否则心跳类逻辑在测试里永远不会触发。
