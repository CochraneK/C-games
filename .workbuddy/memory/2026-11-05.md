## C-games：对「进入房间」改动做第二轮严格自查

上一轮（a09d3e7）号称修好了「对方说进来了、我这边不显示」，本轮不预设它对了，
先写会红的断言再改代码，抓到 6 条真问题（其中 1 条正是上一轮的漏网之鱼）。

### 真问题
1. **广播发给野连接**（最要命）：`broadcast()` 原来遍历所有 `open` 的连接。
   房主给已入座客人发 `room/state` 时，一条还没 join 的连接也会收到，
   客户端拿它 `joined=true` → 显示「已坐下」，房主那边根本没这个人。
   实测失败输出：`7777已坐下 · 未准备315315 · 你已坐下 · 未准备`。
   → 改为只发给 `seatPeer` 里登记过的连接，每个包附 `you`（接收座位）；
     客户端只认 `welcome` 作为入座确认，`room/state` 在 `joined` 前一律忽略，
     并校验 `you===mySeat`。
2. **bfcache 回来是僵尸房间**：`pagehide` 销毁 peer，但脚本不会重跑、也没 `pageshow`。
   返回/前进回到页面后界面还显示在房里，实际收不到任何消息。
   → duel 用 `hardReconnect()` 保座；watch / turtle / bell/multi 用
     `pageshow persisted → location.reload()` 回到可重新加入的状态。
     `bell/app.js` 的 pagehide 不 destroy peer，故意不加（加了反而打断还能用的房间）。
3. **信令重连把「已准备」抹掉**：`onHostReady()` 保留 `here` 但把 ready/voice 重置，
   两边要重新点准备。→ 连房主自己的准备状态一起保留。
4. **CDN 串行最坏 36 秒**：4 个源依次 await、每个 9s 超时。→ 并发抢 + 12s 总超时。
5. **ICE 失败不会新建连接**：只置 `joined=false`，死连接仍留在 `conn` 里，
   `joinHost()` 看 `conn.open` 为真就只补发 join，永远不重建。→ 主动 `conn=null; c.close()`。
6. **依赖私有 API**：原来直接摸 `pc.addEventListener('iceconnectionstatechange')`。
   查 PeerJS v1.5.5 源码（`lib/baseconnection.ts`）确认有公开的
   `iceStateChanged` 事件 + `peerConnection` 属性 → 改用官方事件，这样才能写测试。
   另：`disconnected` 常能自恢复，不该一抖就重连；只处理 failed/closed。

### 方法论
- 「自查」最有效的一招是**先写会红的断言**：把怀疑的场景做成测试，跑一次看它真的红，
  再改代码。比「我看代码觉得没问题」可靠得多，也避免把上一轮的修复当事实。
- 不确定第三方库有没有某个 API 时，去查官方源码（`gh api repos/.../contents/...?ref=<tag>`），
  别凭印象写「尽力而为」的死代码；查到官方事件后还能顺带把这段逻辑纳入测试。

## C-games：跨网络实测仍连不上 → 改用「稳定通道」（纯 HTTPS 中继）

用户实测反馈「好像还是不行」，追问得到两条关键信息：
**症状=他进来了我没显示**、**网络=一边 WiFi 一边手机流量**。这就是无 TURN 时
WebRTC 打不通的典型场景，前面几轮在 PeerJS 层怎么修都治不了本。

### 实测证据（别再猜）
- PeerJS 信令 `https://0.peerjs.com/peerjs/id` → HTTP 200（36B），CDN jsDelivr/unpkg → 200。
  **信令和 CDN 都没问题**，问题只在 DataConnection 的 ICE。
- `openrelay.metered.ca` → `192.0.2.1`（RFC5737 文档保留地址，DNS 黑洞）；
  `staticauth.openrelay.metered.ca` → 真实 IP `216.39.253.123`，但 TCP 80/443 全超时。
  官方已改为「注册免费账号 → REST 拉凭据 / auth-secret」，静态凭据路线作废。
- 本机无 wrangler / 无 CF 登录态 → 自建 Worker 或带凭据 TURN 都需要用户先提供资源。

### 解法：绕开 WebRTC，而不是继续修打洞
两人牌戏每秒只有几条消息，走普通 HTTPS 就够。**ntfy.sh 实测可用**：
- `POST https://ntfy.sh/<topic>` → 200、`Access-Control-Allow-Origin: *`
- `GET  https://ntfy.sh/<topic>/sse` → 200、SSE 实时推送，先订阅再发布能秒收
- 公共实例**不缓存历史**（`?poll=1&since=all` 读回空），所以订阅**不要带 `since=all`**，
  否则可能拿到几小时前的旧状态；默认只推订阅后的新消息最干净。

新增 `bell/duel/relay.html` + `relay.js`（**稳定通道**），与直连版并存：
- 座位 **0=77 固定当裁决端**、1=315 客人 → 不再靠抢注册 PeerJS 固定 id 决定角色，
  彻底没有竞态；规则运算只在 77 端跑 `MultiBellCore`，改完广播快照。
- 客人必须收到 77 的 `state` 回执且 `seats[1].cid===自己` 才 `joined=true`（沿用握手制）。
- topic 用不可猜常量（不直接用房间码）；每条消息带 `v/room/from/seat/ts`，
  用 SSE 的 `outer.id` 去重、`rev` 挡旧包，**不用对端时间戳做过期判断**（设备时钟会偏）。
- 座位冲突用**确定性仲裁**：`lastHello[seat]` 记录最近声明者（哪怕自己还没选座），
  入座瞬间比较 cid 字典序，大的直接让位；否则两人同时坐时先坐那位的 hello 会被忽略，
  两边都显示已占座（这是测试抓出来的真 bug）。
- 房间码 `su77315` 在大厅/多人页的输入框现在**默认跳稳定通道**；
  旧直连版 `duel/` 保留，并在房间栏加「连不上？用稳定通道 ↗」。

### 代价（如实）
- 依赖第三方公共服务 ntfy.sh，国内手机流量下的可达性**尚未经用户真机实测**；
  页面加了 8s 订阅超时，连不上会明确写「中继不可达 · 换个网络试试」，不再干等。
- 稳定通道**不提供语音**（语音需要点对点直连）；同网可切回直连版。
- 消息内容是扑克牌状态，不含隐私，但确实经过第三方中继。

### 验证
`relay-smoke.js` **43 项全过**（连跑 5 次稳定）：两个 vm 客户端用 fake fetch 互投消息，
覆盖房间码、固定座位、握手前不许假装入座、完整对局、玩法切换、座位冲突、离线重连、
SSE 解析、入口静态审计。真实 ntfy 端到端（正式 topic）也实测通过。
原有 duel 100 / smoke / mp / ui / multi 全过；30 个 JS 语法 0 错；7 个 HTML 标签与 id 无异常。

### 教训
- **连续几轮修不好时，要退一步问「这条技术路线本身是不是不成立」**：
  一边 WiFi 一边流量 + 无 TURN = WebRTC 必然打不通，再多的重连/心跳/握手都只是让界面更诚实。
- 别靠「我记得这个免费服务能用」：DNS + TCP + 实际 pub/sub 闭环各测一遍，
  很快就能判定一条路是死是活。
- 双通道并存时，**默认入口给确定性高的那条**，旧版留手动切换，别让用户自己排障。
